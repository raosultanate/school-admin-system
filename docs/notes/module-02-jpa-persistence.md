# Module 2 — Persistence: JPA, Hibernate, Spring Data

Code: `domain/Person.java` (`@MappedSuperclass`), `domain/Student.java`, `domain/Teacher.java`,
`domain/Course.java` (all `@Entity`), `repository/{StudentRepository,TeacherRepository,
CourseRepository}.java`, `StudentRepositoryStartupRunner.java`. See also
[`annotations.md`](annotations.md) for the JPA/Hibernate annotation reference — a
**separate system** from Module 1's Spring DI annotations, worth re-reading that
distinction before this module, not just once.

## The database: H2, in-memory, and completely temporary

H2 is a real SQL database, but written in pure Java so it can run *embedded inside the app's
own process* — no separate database server to install (`com.h2database:h2`, `runtime` scope
in `pom.xml` since Module 0). Running in `mem:` mode means it lives entirely in RAM, not as a
file. Every log line like:

```
Database available at 'jdbc:h2:mem:26808850-00a7-4925-8cce-ae1b93854610'
```

shows a **different random name every run** — confirmed by actually running the app multiple
times and comparing. This is deliberate: **the entire database, schema and data, is
destroyed the moment the app stops**, and rebuilt from nothing the next time it starts. No
"does this already exist" check happens anywhere, because there's never anything left over
to check against. (Module 9 switches to a real, persistent database — Postgres — for
anything meant to survive a restart.)

## `Person` becomes `@MappedSuperclass` — the design problem first

Two real conflicts existed before any entity code could be written:

1. **`private final` fields, no no-arg constructor.** Hibernate builds entity objects via
   reflection — calls a no-arg constructor to get a blank object, *then* sets each field
   afterward. `final` fields can only be assigned once, inside a constructor; that's
   incompatible with "build empty, fill in later."
2. **No `id` field.** Every entity needs a primary key, and since the fields an id would sit
   alongside (`firstName`/`lastName`/`email`) live on `Person`, the id belongs there too —
   not duplicated into every subclass.

Three ways to solve this were considered:

- **Full JPA inheritance** (`Person` itself `@Entity`, with an `@Inheritance` strategy) — the
  "most correct" mirror of the OOP hierarchy, making `Person` genuinely queryable across
  subtypes. Rejected for now: real complexity (`SINGLE_TABLE` = one table with lots of
  nullable columns; `JOINED` = a join on every read) for a need that doesn't exist yet.
- **Give up on sharing `Person`** — duplicate the fields into `Student`/`Teacher` directly.
  Rejected: throws away the OOP hierarchy `java-refresher` built and that `PersonService`
  already depends on.
- **`@MappedSuperclass`** (chosen) — fields written once on `Person`, flattened as real
  columns into each subclass's own separate table. No join, no shared table, no inheritance
  strategy to pick. Trade-off: `Person` isn't queryable on its own — nothing needs that yet.

```java
@MappedSuperclass
public abstract class Person {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;   // no longer final
    // ...

    protected Person() {        // required by JPA, never called by application code
    }

    protected Person(String firstName, String lastName, String email) {   // unchanged, still used normally
        // ...
    }
}
```

The 3-argument constructor wasn't removed — Java allows multiple constructors
(overloading). Application code and tests still call it exactly as before; only Hibernate
ever calls the new no-arg one, and only when reconstructing an object from a database row.

`@MappedSuperclass` has **nothing to do with Spring's container** — no bean gets created
because of it, component scanning doesn't look at it. It's read by Hibernate alone, a
completely separate annotation system from Module 1's.

## `@Id`/`@GeneratedValue`: an auto-generated primary key

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

`@Id` marks the primary key. `@GeneratedValue(strategy = IDENTITY)` means the *database*
produces the value on insert — confirmed directly in the generated DDL:

```sql
id bigint generated by default as identity,
```

Consequence worth internalizing: **the `Student` constructor takes no `id` parameter, on
purpose.** At the moment `new Student(...)` runs, the object only exists in Java memory — no
row has been inserted yet, so there's no id to give it. Confirmed live:

```
Before save: id = null
After save:  id = 1
```

`id` goes from `null` to `1` at the exact moment `.save()` actually runs — Hibernate writes
the database-generated value into the object's private `id` field via reflection afterward,
same mechanism as the no-arg constructor (no `setId()` method exists or is needed).

## `Student` — the first real `@Entity`

```java
@Entity
@Table(name = "students")
public class Student extends Person {

    @Column(nullable = false, unique = true)
    private String studentNumber;

    private int enrollmentYear;

    protected Student() {
    }
    // ... existing 5-arg constructor unchanged
}
```

`@Table(name = "students")` is explicit rather than relying on Hibernate's default naming
(which would produce the singular `student`, not `students`). `@Column(nullable = false,
unique = true)` on `studentNumber` moves what `StudentRegistry` (`java-refresher`, Module 3)
checked by hand with a linear `List` scan into a real database constraint — a duplicate
insert now fails at the database level. Turning that failure into a proper HTTP error
response is Module 4 (Validation & Exception Handling in Spring).

Confirmed live — the generated table matches exactly:

```sql
create table students (
    enrollment_year integer not null,
    id bigint generated by default as identity,
    email varchar(255),
    first_name varchar(255),
    last_name varchar(255),
    student_number varchar(255) not null unique,
    primary key (id)
)
```

`id`/`email`/`first_name`/`last_name` came from `Person` (via `@MappedSuperclass`);
`enrollment_year`/`student_number` came from `Student` itself — one flat table, no join,
exactly as designed.

## `Teacher` — mapping an enum field

```java
@Enumerated(EnumType.STRING)
private Department department;
```

Without `@Enumerated`, Hibernate's default is `EnumType.ORDINAL` — storing the constant's
*declaration position* (0, 1, 2...) as a plain integer. That breaks silently the moment
`Department`'s constants are reordered or a new one is inserted in the middle — a row that
meant `COMPUTER_SCIENCE` could silently become `MATHEMATICS` after a code change, no error,
just wrong data. `STRING` stores the constant's actual name instead.

Confirmed live — H2 happened to map this to its own native `enum` SQL type (not a plain
`varchar`, which was the expectation going in — H2 supports enums natively):

```sql
department enum ('COMPUTER_SCIENCE','HISTORY','MATHEMATICS')
```

## `Course` — a standalone entity

```java
@Entity
@Table(name = "courses")
public class Course {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    private int capacity;
    // ...
}
```

`Course` isn't a `Person` subtype — it's an unrelated concept, so it gets its own `@Id`
directly rather than inheriting one from a `@MappedSuperclass`. First entity in this project
that didn't already exist as a plain-Java class before this module.

## `JpaRepository<T, ID>` — same shape as `InMemoryRepository`

```java
public interface StudentRepository extends JpaRepository<Student, Long> {
}
```

An interface with no methods and no class implementing it — genuinely correct, not
incomplete. At startup, Spring Data JPA scans for interfaces extending `JpaRepository` and
**generates a real implementing class at runtime** for each one, registered as a bean the
same way `PersonService` was in Module 1. `extends JpaRepository<Student, Long>` alone
already provides `save()`, `findById()`, `findAll()`, `deleteById()`, `count()` — no SQL, no
implementation, written anywhere.

`<Student, Long>` is the exact same two-type-parameter shape as `java-refresher`'s
hand-rolled `InMemoryRepository<T, ID>` (Module 4 there) — `T` the entity type, `ID` its
primary key's type. That hand-rolled version was deliberately foreshadowing this one.

Confirmed live, end to end:

```java
Student saved = studentRepository.save(ada);          // INSERT INTO students ...
Optional<Student> found = studentRepository.findById(saved.getId());   // SELECT ... WHERE id=?
```

```
Before save: id = null
After save: id = 1
findById(1): Ada Lovelace is a student (#S-1001, enrolled 2024)
```

## Derived query methods

```java
Optional<Student> findByStudentNumber(String studentNumber);
```

No method body, no annotation even — Spring Data **parses the method name itself**
(`findBy` + `StudentNumber`) and generates the query from that alone, at startup. Confirmed
live, generated SQL:

```sql
select ... from students s1_0 where s1_0.student_number=?
```

```
findByStudentNumber("S-1001"): Ada Lovelace is a student (#S-1001, enrolled 2024)
findByStudentNumber("S-9999"): not found
```

This is the same lookup `StudentRegistry.findByStudentNumber()` (`java-refresher`) did with a
manual linear scan — here the database does the lookup directly, and the method name is the
only thing that had to be written correctly for it to work.

## H2 console

Confirmed available every run via the startup log (`H2 console available at
'/h2-console'`) — a browser UI at `http://localhost:8080/h2-console` for poking at the live
database directly while the app is running, using the JDBC URL/credentials (`SA`, no
password) printed in that same log line. Not yet used for anything beyond confirming it's
reachable; genuinely useful once there's more than one table's worth of data to look at by
hand.
